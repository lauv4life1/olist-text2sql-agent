# 口径登记表（Single Source of Truth）

> 本表是本项目全部指标口径的**唯一真源**。基线 SQL（`02_sql/`）、Agent prompt（`03_agent/prompt_builder.py`）、
> few-shot、评估指标（`03_agent/evaluate.py` 的 `CORE_COLS`）必须与本表一致；任何一处不一致即为 bug。
>
> 变更流程：本表定稿 → 改基线 SQL → 重跑 `sql_answers.py` 生成基线 → 改 prompt / few-shot / CORE_COLS
> → 重跑 `evaluate.py` 验证。**五步走完才算改完。**

## 一、已定口径

### 基础指标口径

| 编号 | 口径项 | 取值 | 落地位置 |

### 时间与时长口径

| 编号 | 口径项 | 取值 | 落地位置 |
|------|--------|------|----------|
| C5 | 配送时长算法 | `TIMESTAMPDIFF(DAY, order_purchase_timestamp, order_delivered_customer_date)`，**禁止 `DATEDIFF`** | 基线 Q5/Q8 + prompt + few-shot |
| C17 | "按月 / 按年"的时间字段 | `orders.order_purchase_timestamp`（**下单时间**）；禁止 `shipping_limit_date` 等发货相关列 | 基线 + prompt |

### 分母 / 总体口径（本次新增）

| 编号 | 口径项 | 取值 | 落地位置 |
|------|--------|------|----------|
| C19 | 州订单数的分母 | 只统计**有支付记录**的订单——**各州订单数之和必须等于平台总订单数 99,440**；不要用 `orders` 直接 JOIN `customers` 计数（会多出无支付记录的订单） | 基线 Q5 + prompt + **caliber_guard** |
| C20 | 州分布的实现 | 必须同时输出 **订单数 + GMV + 平均配送时长** 三列；先按"订单粒度"算好（`order_payments` 先 `GROUP BY order_id` 求和），再与 orders/customers 内连接按州聚合，避免被多支付行放大 | 基线 Q5 + prompt + few-shot + **caliber_guard** |
| C14 | 高价值客户的总体 | 客户总体 = **有支付记录的订单**所覆盖的全部 `customer_unique_id`（实测 **96,095** 人，恰好 5 档、每档 **19,219** 人）；不做任何额外过滤（不要求已签收 / 不要求有评价 / 不要求有金额）；按 `SUM(payment_value)` 汇总后 `NTILE(5)` | 基线 Q10 + prompt + **caliber_guard** |
| C21 | 聚合的粒度（禁止扇出） | 金额 / 时长的聚合必须发生在**订单粒度**：`order_payments`、`order_items` 对同一订单是**多行**，直接 `JOIN` 后再 `SUM` / `AVG` 会按"订单行数"加权（`COUNT(DISTINCT order_id)` 只能救计数，救不了 `SUM`/`AVG`）。正确做法：先按 `order_id` 预聚合成一单一行，再在订单粒度聚合 | prompt + **caliber_guard**（C21） |
| C22 | 分层结果的三个量 | 高价值客户分层必须输出**人数**、**人均消费**、**人均单数**，三者量纲不同；结果中**任意两列取值逐行相同即为错误**（典型：把 `SUM(total_spend)/COUNT(*)` 写成"人均单数"，其实那是人均消费）。人均单数用 `COUNT(DISTINCT order_id)` 按客户统计后再取平均，量级 ~1 | prompt + **caliber_guard**（C22） |
| C23 | **守恒式断言的作用域前提** | 守恒式（C1 / C19 / C14）只在**分组覆盖全集**时成立。SQL 带 `LIMIT`、或按 `ROW_NUMBER / RANK / NTILE` 取前 N 时，结果只是总体的**部分视图** → 守恒断言**主动跳过**（前提不成立时宁可不判，也不误报）。反之，不带截断时断言必须照常生效 | **`caliber_guard._is_truncated_scope`**（C1 / C19 / C20 的闸门） |

## 二、口径的落地：四层防线（口径不是文档，是可执行的断言）

口径写进文档只是第一步，**能不能被执行层强制住**才是关键。本项目把口径落到四层：

| 层 | 组件 | 能抓住什么 | 抓不住什么 | 反馈方式 |
|---|---|---|---|---|
| **0 意图** | `agent._looks_like_sql` | 模型**没输出 SQL**（拒答 / 自然语言说明） | — | 显式 `CANNOT_ANSWER` 协议，不当作校验失败 |
| 1 安全 | `sql_validator._check_safety` | 写操作、多语句、锁子句、敏感表 | 一切业务错误 | 拒绝执行 |
| 2 语法 | `sql_validator._check_syntax`（`EXPLAIN`） | 语法 / 表列名拼错、`1064` | 跑得通但算错的 SQL | 回传 MySQL 报错 |
| 3 schema | `sql_validator._check_schema` | 幻觉表名 / 列名 | 语义与粒度错误 | 回传未知标识符 |
| **3.5 执行** | `sql_executor.SqlExecutionError` | **`EXPLAIN` 通不了、只有真跑才暴露的错误**（标量子查询返回多行、超时 `3024`） | — | 回传执行期报错，**不崩** |
| 4 **口径** | **`caliber_guard.py`** | **扇出、分母错、总体过度过滤、输出缺列** | 主观业务判断 | **结构化口径反馈回灌** |

第 4 层为什么必须存在：扇出、分母口径错这类错误，SQL **语法完全合法、`EXPLAIN` 也过**，
只有拿到**结果集**才能发现。所以第 4 层不是"再检查一遍 SQL"，而是**用结果反推口径**。

第 3.5 层为什么必须存在（高压测试实测）：`EXPLAIN` **只做解析与优化、不真正执行**，
所以"语法合法但跑不出来"的 SQL 会穿透第 1~3 层，直接在执行器抛异常。
早期 `agent.ask()` 没兜这个异常，一次 `Subquery returns more than 1 row` 就能把整个 Agent 打崩。

第 0 层为什么必须存在（高压测试实测）：问"客户的年龄分布"时，模型正确地判断出
"customers 表没有出生日期字段"，于是**输出了一段中文说明而不是 SQL**。
这段说明被当成 SQL 灌进校验层，得到 `只允许 SELECT / WITH 查询`，
然后被当成"SQL 写错了"重试 3 次 —— **把"答不了"误判成"写错了"**。
现在改为显式协议：确实答不了就输出 `CANNOT_ANSWER: <原因>`，Agent 直接以
`status="unanswerable"` 返回该说明，不再消耗重试预算。

### 第 4 层的守恒断言（唯一的四组硬约束）

| 断言 | 对应口径 | 守恒式 | 抓的历史真实错误 |
|---|---|---|---|
| 全局总量守恒 | C1 / C15 | 单行结果的 `total_orders = 99,440`；实付口径 `gmv = 16,008,872.12`、售价口径 `price 合计 = 13,591,643.70`（按 SQL 实际用的口径选参照值） | 用 `orders` 单表数订单 → 99,441 |
| 州维度守恒 | C19 / C15 | 各州订单数之和 `= 99,440`；各州金额之和 `=` 对应口径的平台总额（实付 `16,008,872.12` / 售价 `13,591,643.70`） | 41,746 ≠ 41,745；GMV 被 JOIN 放大 |
| 州输出齐全 | C20 | 出现州列时必须有三列（订单数 / GMV / 时长） | 只给订单数，漏 GMV / 时长 |
| 分层总体守恒 | C14 | 各档客户数之和 `= 96,095`（5 × 19,219） | 18,672 / 21,145（总体被过滤成"已签收/有评价"） |
| 无扇出 | C21 | `JOIN order_payments / order_items` 后求 `AVG(TIMESTAMPDIFF)` 必须已有 `GROUP BY order_id`（或走子查询 `IN`） | DeepSeek Q5：时长被一单多付扇出加权 |
| 分层列不重复 | C22 | 分层结果里任意两个数值列不得逐行取值相同 | 两个 GLM 都把"人均单数"写成 `SUM(total_spend)/COUNT(*)`，与 `avg_spend` 完全相同 |

**关键设计**：断言只依赖**结果形状**（有没有州列 / 分位列 / 单行总量）与 SQL 文本，
**与题号解耦** —— 新增题目只要形状命中就自动被保护。

**关键克制（C23）**：守恒式有前提 —— **分组必须覆盖全集**。所以断言自带一道闸门
`_is_truncated_scope`：SQL 带 `LIMIT` / 排名取前 N 时**主动跳过**。
不加这道闸门，第 4 层会把**正确答案**判成错的（实测：问"各州客单价排名前十"，
正确 SQL 被 C19 判成"订单数之和 3497 ≠ 99440"、被 C20 判成"缺平均配送时长"，
反复回灌改错后标成 `caliber_ok=false`）。
**误报比漏报更伤**：漏报少抓一个错，误报会把对的改坏。

### 守恒量的镜像关系

守恒量有两份，必须同步：`CALIBER.md`（人读，唯一真源）↔ `caliber_guard.py` 顶部的常量（机读）。
`caliber_check.py` 会检查两者的漂移，`tests/test_caliber_guard.py` 覆盖每条断言的**正例与反例**。

### 反馈回灌的形态（"结构化"体现在哪）

回灌给模型的不是"你错了"，而是**定位到列 + 口径编号 + 正确写法**，例如：

```
【口径校验未通过】上一次生成的 SQL 能正常执行，但结果违反了以下数据口径，请针对性修正后重新输出 SQL：
1. [C19] 按州统计的订单数之和 = 99441，应为平台总订单数 99440（相差 +1）。
   订单数口径是「只统计有支付记录(order_payments)的订单」——用 orders 直接 JOIN customers
   数订单会多算无支付记录的订单。正确写法：…
只修正上述问题，不要改动问题里其它已经正确的口径。
```

口径反馈与静态校验反馈**共用同一份重试预算**（`MAX_RETRIES`），模型因此是"改到对为止"而非"跑通就交"。
